OpenStack 上的 OpenShift：更好地交付應用程序 ​

你有沒有問過自己，我應該在哪裏運行 OpenShift？答案是任何地方 - 它可以在裸機、虛擬機、私有云或公共雲中很好地運行。但是，這裏有一些為什麼人們正遷移到圍繞全棧和資源消耗自動化相關的私有云和公有云的原因。傳統的操作系統一直是關於硬件資源的展示和消耗 - 硬件提供資源，應用程序消耗它們，操作系統一直是交通警察。但傳統的操作系統一直侷限於單機^注1 。

那麼，在原生雲的世界裏，現在意味着這個概念擴展到包括多個操作系統實例。這就是 OpenStack 和 OpenShift 所在。在原生雲世界，虛擬機、存儲卷和網段都成為動態配置的構建塊。我們從這些構建塊構建我們的應用程序。它們通常按小時或分鐘付費，並在不再需要時被取消配置。但是，你需要將它們視為應用程序的動態配置能力。 OpenStack 在動態配置能力（展示）方面非常擅長，OpenShift 在動態配置應用程序（消費）方面做的很好，但是我們如何將它們結合在一起來提供一個動態的、高度可編程的多節點操作系統呢？

要理解這個，讓我們來看看如果我們在傳統的環境中安裝 OpenShift 會發生什麼 - 想像我們想要為開發者提供動態訪問來創建新的應用程序，或者想像我們想要提供業務線，使其能夠訪問現有應用程序的新副本以滿足合同義務。每個應用程序都需要訪問持久存儲。持久存儲不是臨時的，在傳統的環境中，這通過提交一張工單實現。沒關係，我們可以連到 OpenShift，每次需要存儲時都會提交一張工單。存儲管理員可以登錄企業存儲陣列並根據需要刪除卷，然後將其移回 OpenShift 以滿足應用程序。但這將是一個非常慢的手動過程，而且你可能會遇到存儲管理員辭職。

在原生雲的世界裏，我們應該將其視為一個策略驅動的自動化流程。存儲管理員變得更加戰略性、設置策略、配額和服務級別（銀、黃金等），但實際配置變得動態。

動態過程可擴展到多個應用程序 - 這可能是開發者測試的業務線甚至新應用程序。從 10 多個應用程序到 1000 個應用程序，動態配置提供原生雲體驗。

下面的演示視頻展示了動態存儲配置如何與 Red Hat OpenStack 平台（Cinder 卷）以及 Red Hat OpenShift 容器平台配合使用，但動態配置並不限於存儲。想像一下，隨着 OpenShift 的一個實例需要更多的容量、節點自動擴展的環境。想像一下，推送一個敏感的程序更改前，將網段劃分為負載測試 OpenShift 的特定實例。這些是你為何需要動態配置 IT 構建塊的原因。OpenStack 實際上是以 API 驅動的方式實現的。

YOUTUBE VIDEO

OpenShift 和 OpenStack 一起更好地交付應用程序。OpenStack 動態提供資源，而 OpenShift 會動態地消耗它們。它們一起為你所有的容器和虛擬機需求提供靈活的原生雲解決方案。

注1：高可用性集羣和一些專門的操作系統在一定程度上彌合了這一差距，但在計算中通常是一個邊緣情況。
