學會愛上 systemd ​

systemd 是所有進程之母，負責將 Linux 主機啓動到可以做生產性任務的狀態。

systemd（是的，全小寫，即使在句子開頭也是小寫），是初始化程序（init）和 SystemV 初始化腳本的現代替代者。此外，它還有更多功能。

當我想到 init 和 SystemV 初始化時，像大多數系統管理員一樣，我想到的是 Linux 的啓動和關閉，而不是真正意義上的管理服務，例如在服務啓動和運行後對其進行管理。像 init 一樣，systemd 是所有進程之母，它負責使 Linux 主機啓動到可以做生產性任務的狀態。systemd 設定的一些功能比老的初始化程序要廣泛得多，它要管理正在運行的 Linux 主機的許多方面，包括掛載文件系統、管理硬件、處理定時器以及啓動和管理生產性主機所需的系統服務。

本系列文章是基於我的三期 Linux 培訓課程《使用和管理 Linux：從零開始進行學習系統管理》部分內容的摘錄，探討了 systemd 在啓動和啓動完成後的功能。

Linux 引導 ​

Linux 主機從關機狀態到運行狀態的完整啓動過程很複雜，但它是開放的並且是可知的。在詳細介紹之前，我將簡要介紹一下從主機硬件被上電到系統準備好用户登錄的過程。大多數時候，“引導過程”被作為一個整體來討論，但這是不準確的。實際上，完整的引導和啓動過程包含三個主要部分：

  • 硬件引導：初始化系統硬件
  • Linux 引導boot：加載 Linux 內核和 systemd
  • Linux 啓動startup：systemd 為主機的生產性工作做準備

Linux 啓動階段始於內核加載了 init 或 systemd（取決於具體發行版使用的是舊的方式還是還是新的方式）之後。init 和 systemd 程序啓動並管理所有其它進程，它們在各自的系統上都被稱為“所有進程之母”。

將硬件引導與 Linux 引導及 Linux 啓動區分開，並明確定義它們之間的分界點是很重要的。理解它們的差異以及它們每一個在使 Linux 系統進入生產狀態所起的作用，才能夠管理這些進程，並更好地確定大部分人所謂的“啓動”問題出在哪裏。

啓動過程按照三步引導流程，使 Linux 計算機進入可進行生產工作的狀態。當內核將主機的控制權轉移到 systemd 時，啓動環節開始。

systemd 之爭 ​

systemd 引起了系統管理員和其它負責維護 Linux 系統正常運行人員的廣泛爭議。在許多 Linux 系統中，systemd 接管了大量任務，這在某些開發者和sysadmins羣體中引起了反對和不和諧。

SystemV 和 systemd 是執行 Linux 啓動環節的兩種不同的方法。SystemV 啓動腳本和 init 程序是老的方法，而使用目標target的 systemd 是新方法。儘管大多數現代 Linux 發行版都使用較新的 systemd 進行啓動、關機和進程管理，但仍有一些發行版未採用。原因之一是某些發行版維護者和系統管理員喜歡老的 SystemV 方法，而不是新的 systemd。

我認為兩者都有其優勢。

為何我更喜歡 SystemV ​

我更喜歡 SystemV，因為它更開放。使用 Bash 腳本來完成啓動。內核啓動 init 程序（這是一個編譯後的二進制）後，init 啓動 rc.sysinit 腳本，該腳本執行許多系統初始化任務。rc.sysinit 執行完後，init 啓動 /etc/rc.d/rc 腳本，該腳本依次啓動 /etc/rc.d/rcX.d 中由 SystemV 啓動腳本定義的各種服務。其中 X 是待啓動的運行級別號。

除了 init 程序本身之外，所有這些程序都是開放且易於理解的腳本。可以通讀這些腳本並確切瞭解整個啓動過程中發生的事情，但是我不認為有太多系統管理員真正做到這一點。每個啓動腳本都被編了號，以便按特定順序啓動預期的服務。服務是串行啓動的，一次只能啓動一個服務。

systemd 是由 Red Hat 的 Lennart Poettering 和 Kay Sievers 開發的，它是一個由大型的、編譯的二進制可執行文件構成的複雜系統，不訪問其源碼就無法理解。它是開源的，因此“訪問其源代碼”並不難，只是不太方便。systemd 似乎表現出對 Linux 哲學多個原則的重大駁斥。作為二進制文件，systemd 無法被直接打開供系統管理員查看或進行簡單更改。systemd 試圖做所有事情，例如管理正在運行的服務，同時提供明顯比 SystemV 更多的狀態信息。它還管理硬件、進程、進程組、文件系統掛載等。systemd 幾乎涉足於現代 Linux 主機的每個方面，使它成為系統管理的一站式工具。所有這些都明顯違反了“程序應該小，且每個程序都應該只做一件事並做好”的原則。

為何我更喜歡 systemd ​

我更喜歡用 systemd 作為啓動機制，因為它會根據啓動階段並行地啓動儘可能多的服務。這樣可以加快整個的啓動速度，使得主機系統比 SystemV 更快地到達登錄屏幕。

systemd 幾乎可以管理正在運行的 Linux 系統的各個方面。它可以管理正在運行的服務，同時提供比SystemV 多得多的狀態信息。它還管理硬件、進程和進程組、文件系統掛載等。systemd 幾乎涉足於現代 Linux 操作系統的每方面，使其成為系統管理的一站式工具。（聽起來熟悉吧？）

systemd 工具是編譯後的二進制文件，但該工具包是開放的，因為所有配置文件都是 ASCII 文本文件。可以通過各種 GUI 和命令列工具來修改啓動配置，也可以添加或修改各種配置文件來滿足特定的本地計算環境的需求。

真正的問題 ​

你認為我不能喜歡兩種啓動系統嗎？我能，我會用它們中的任何一個。

我認為，SystemV 和 systemd 之間大多數爭議的真正問題和根本原因在於，在系統管理層面沒有選擇權。使用 SystemV 還是 systemd 已經由各種發行版的開發人員、維護人員和打包人員選擇了（但有充分的理由）。由於 init 極端的侵入性，挖出並替換 init 系統會帶來很多影響，會帶來很多在發行版設計過程之外難以解決的後果。

儘管該選擇實際上是為我而選的，但我的Linux主機能不能開機、能不能工作，這是我平時最關心的。作為最終用户，甚至是系統管理員，我主要關心的是我是否可以完成我的工作，例如寫我的書和這篇文章，安裝更新以及編寫腳本來自動化所有事情。只要我能做我的工作，我就不會真正在意發行版中使用的啓動系統。

在啓動或服務管理出現問題時，我會在意。無論主機上使用哪種啓動系統，我都足夠了解如何沿着事件順序來查找故障並進行修復。

替換SystemV ​

以前曾有過用更現代的東西替代 SystemV 的嘗試。大約在兩個版本中，Fedora 使用了一個叫作 Upstart 的東西來替換老化的 SystemV，但是它沒有取代 init，也沒有提供我所注意到的任何變化。由於 Upstart 並未對 SystemV 的問題進行任何顯著的改變，所以在這個方向上的努力很快就被放棄了，轉而使用 systemd。

儘管大部分 Linux 開發人員都認可替換舊的 SystemV 啓動系統是個好主意，但許多開發人員和系統管理員並不喜歡 systemd。與其重新討論人們在 systemd 中遇到的或曾經遇到過的所有所謂的問題，不如帶你去看兩篇好文章，儘管有些陳舊，但它們涵蓋了大多數內容。Linux 內核的創建者 Linus Torvalds 對 systemd 似乎不感興趣。在 2014 年 ZDNet 的一篇文章《Linus Torvalds 和其他人對 Linux 上的 systemd 的看法》中，Linus 清楚地表達了他的感受。

“實際上我對 systemd 本身沒有任何特別強烈的意見。我對一些核心開發人員有一些問題，我認為他們在對待錯誤和兼容性方面過於輕率，而且我認為某些設計細節是瘋狂的（例如，我不喜歡二進制日誌），但這只是細節，不是大問題。”

如果你對 Linus 不太瞭解的話，我可以告訴你，如果他不喜歡某事，他是非常直言不諱的，很明確，而且相當明確的表示不喜歡。他解決自己對事物不滿的方式已經被社會更好地接受了。

2013 年，Poettering 寫了一篇很長的Blog，他在文章駁斥了關於 systemd 的迷思，同時對創建 systemd 的一些原因進行了深入的剖析。這是一分很好的讀物，我強烈建議你閲讀。

systemd 任務 ​

根據編譯過程中使用的選項（不在本系列中介紹），systemd 可以有多達 69 個二進制可執行文件執行以下任務，其中包括：

  • systemd 程序以 1 號進程（PID 1）運行，並提供使盡可能多服務並行啓動的系統啓動能力，它額外加快了總體啓動時間。它還管理關機順序。
  • systemctl 程序提供了服務管理的用户接口。
  • 支持 SystemV 和 LSB 啓動腳本，以便向後兼容。
  • 服務管理和報告提供了比 SystemV 更多的服務狀態數據。
  • 提供基本的系統配置工具，例如主機名、日期、語言環境、已登錄用户的列表，正在運行的容器和虛擬機、系統帳户、運行時目錄及設置，用於簡易網絡配置、網絡時間同步、日誌轉發和名稱解析的守護進程。
  • 提供套接字管理。
  • systemd 定時器提供類似 cron 的高級功能，包括在相對於系統啓動、systemd 啓動時間、定時器上次啓動時間的某個時間點運行腳本。
  • 它提供了一個工具來分析定時器規範中使用的日期和時間。
  • 能感知分層的文件系統掛載和卸載功能可以更安全地級聯掛載的文件系統。
  • 允許主動的創建和管理臨時文件，包括刪除。
  • D-Bus 的接口提供了在插入或移除設備時運行腳本的能力。這允許將所有設備（無論是否可插拔）都被視為即插即用，從而大大簡化了設備的處理。
  • 分析啓動環節的工具可用於查找耗時最多的服務。
  • 它包括用於存儲系統消息的日誌以及管理日誌的工具。

作為 1 號進程的 systemd ​

systemd 是 1 號進程（PID 1）。它的一些功能，比老的 SystemV3 init 要廣泛得多，用於管理正在運行的 Linux 主機的許多方面，包括掛載文件系統以及啓動和管理 Linux 生產主機所需的系統服務。與啓動環節無關的任何 systemd 任務都不在本文討論範圍之內（但本系列後面的一些文章將探討其中的一些任務）。

首先，systemd 掛載 /etc/fstab 所定義的文件系統，包括所有交換文件或分區。此時，它可以訪問位於 /etc 中的配置文件，包括它自己的配置文件。它使用其配置鏈接 /etc/systemd/system/default.target 來確定將主機引導至哪個狀態或目標。default.target 文件是指向真實目標文件的符號鏈接。對於桌面工作站，通常是 graphical.target，它相當於 SystemV 中的運行級別 5。對於服務器，默認值更可能是 multi-user.target，相當於 SystemV 中的運行級別 3。emergency.target 類似於單用户模式。目標target和服務service是 systemd 的單元unit。

圖 3: systemd 啓動圖

sysinit.target 和 basic.target 目標可以看作啓動過程中的檢查點。儘管 systemd 的設計目標之一是並行啓動系統服務，但是某些服務和功能目標必須先啓動，然後才能啓動其它服務和目標。直到該檢查點所需的所有服務和目標被滿足後才能通過這些檢查點。

當 sysinit.target 所依賴的所有單元都完成時，就會到達 sysinit.target。所有這些單元，包括掛載文件系統、設置交換文件、啓動 Udev、設置隨機數生成器種子、啓動低層服務以及配置安全服務（如果一個或多個文件系統是加密的）都必須被完成，但在 sysinit.target 中，這些任務可以並行執行。

sysinit.target 啓動了系統接近正常運行所需的所有低層服務和單元，它們也是進入 basic.target 所需的。

在完成 sysinit.target 之後，systemd 會啓動實現下一個目標所需的所有單元。basic.target 通過啓動所有下一目標所需的單元來提供一些額外功能。包括設置為各種可執行程序目錄的路徑、設置通信套接字和計時器之類。

最後，用户級目標 multi-user.target 或 graphical.target 被初始化。要滿足 graphical.target 的依賴必須先達到 multi-user.target。圖 3 中帶下劃線的目標是通常的啓動目標。當達到這些目標之一時，啓動就完成了。如果 multi-user.target 是默認設置，那麼你應該在控制台上看到文本模式的登錄界面。如果 graphical.target 是默認設置，那麼你應該看到圖形的登錄界面。你看到的具體的 GUI 登錄界面取決於你的默認顯示管理器。

引導手冊頁還描述並提供了引導到初始化 RAM 磁盤和 systemd 關機過程的圖。

systemd 還提供了一個工具，該工具列出了完整的啓動過程或指定單元的依賴項。單元是一個可控的 systemd 資源實體，其範圍可以從特定服務（例如 httpd 或 sshd）到計時器、掛載、套接字等。嘗試以下命令並滾動查看結果。

systemctl list-dependencies graphical.target

注意，這會完全展開使系統進入 graphical.target 運行模式所需的頂層目標單元列表。也可以使用 --all 選項來展開所有其它單元。

systemctl list-dependencies --all graphical.target

你可以使用 less 命令來搜索諸如 target、slice 和 socket 之類的字符串。

現在嘗試下面的方法。

systemctl list-dependencies multi-user.target

和

systemctl list-dependencies rescue.target

和

systemctl list-dependencies local-fs.target

和

systemctl list-dependencies dbus.service

這個工具幫助我可視化我正用的主機的啓動依賴細節。繼續花一些時間探索一個或多個 Linux 主機的啓動樹。但是要小心，因為 systemctl 手冊頁包含以下注釋：

“請注意，此命令僅列出當前被服務管理器加載到內存的單元。尤其是，此命令根本不適合用於獲取特定單元的全部反向依賴關係列表，因為它不會列出被單元聲明瞭但是未加載的依賴項。”

結尾語 ​

即使在沒有深入研究 systemd 之前，很明顯能看出它既強大又複雜。顯然，systemd 不是單一、龐大、獨體且不可知的二進制文件。相反，它是由許多較小的組件和旨在執行特定任務的子命令組成。

本系列的下一篇文章將更詳細地探討 systemd 的啓動，以及 systemd 的配置文件，更改默認的目標以及如何創建簡單服務單元。
